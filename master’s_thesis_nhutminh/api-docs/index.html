PlateReader LR — API Docs

Backend FastAPI cho prototype MF-SR-OCR (roadmap 12 tuần, §2 và Tuần 2/7). Phiên bản API: 1.0.0 · Base URL: http://localhost:8000/api/v1 Swagger UI tương tác (sinh tự động): http://localhost:8000/api/v1/docs

Tài liệu Nội dung

database-schema.md Mô tả 3 bảng PostgreSQL batches, predictions, reviews

Danh sách endpoint

# Method Path Mô tả Roadmap
1 GET /health Trạng thái service (model + DB) /health · Tuần 2
2 GET /model Thông tin model đang phục vụ Tuần 6 (freeze manifest)
3 POST /predictions Nhận dạng 1 track (1–5 frame) /predict · Tuần 2
4 GET /predictions Danh sách prediction, lọc theo status/batch_id Tab Review · Tuần 8
5 GET /predictions/{id} Chi tiết 1 prediction Tuần 7
6 DELETE /predictions/{id} Xoá 1 prediction —
7 GET /predictions/{id}/suggestions Gợi ý top-k biển số thay thế cho người review Tab Review · Tuần 8
8 PUT /predictions/{id}/review Ghi kết quả sửa tay "người review sửa → DB" · §2
9 POST /batches Tạo batch job từ file zip /predict_batch · Tuần 7
10 GET /batches Danh sách batch Tab Batch · Tuần 8
11 GET /batches/{id} Trạng thái / tiến độ / accuracy của batch Tuần 7
12 GET /batches/{id}/predictions Kết quả từng track của batch Tab Batch · Tuần 8
13 GET /batches/{id}/export Xuất CSV "zip → CSV" · Tuần 7
14 DELETE /batches/{id} Xoá batch + toàn bộ prediction —

Ánh xạ với roadmap. Roadmap §2 ghi /health, /predict, /predict_batch. API giữ đúng 3 chức năng đó nhưng đặt tên theo REST: danh từ số nhiều cho resource, method HTTP thể hiện hành động. POST /predict → POST /predictions, POST /predict_batch → POST /batches + GET /batches/{id}/export. Response giữ nguyên tên trường của roadmap: plate, char_conf[], track_conf, status, sr_images[], latency_ms, model_version.

Quy ước chung

Định dạng

  • Request upload dùng multipart/form-data; các request khác dùng application/json.
  • Response thành công là application/json (riêng /export là text/csv).
  • Thời gian theo ISO 8601 kèm múi giờ, ví dụ 2026-10-22T22:55:00.756+07:00.
  • ID là UUID v4. Nếu path chứa ID sai định dạng, API trả 422 validation_error.
  • Biển số luôn ở dạng IN HOA, không có khoảng trắng.

Mã trạng thái HTTP

Code Khi nào
200 OK GET / PUT thành công
201 Created POST /predictions, kèm header Location: /api/v1/predictions/{id}
202 Accepted POST /batches: job đã vào hàng đợi, header Location: /api/v1/batches/{id}
204 No Content DELETE thành công
404 Not Found Không có resource
409 Conflict Thao tác không hợp lệ với trạng thái hiện tại (export batch chưa xong, xoá batch đang chạy)
413 Content Too Large File vượt giới hạn (ảnh > 5 MB, zip > 200 MB, > 5000 track)
415 Unsupported Media Type Sai kiểu file (không phải JPG/PNG/ZIP)
422 Unprocessable Entity Dữ liệu sai: ảnh hỏng, số frame ∉ [1, 5], query sai enum…
503 Service Unavailable Model chưa load, DB mất kết nối / quá tải (có Retry-After)

Định dạng lỗi (RFC 9457 — application/problem+json)

Mọi lỗi đều có cùng một dạng, nên frontend chỉ cần một hàm xử lý lỗi duy nhất. Trường code ổn định, dùng được để rẽ nhánh xử lý.

{
  "type": "https://platereader.local/problems/invalid_frame_count",
  "title": "Invalid frame count",
  "status": 422,
  "detail": "Cần 1–5 ảnh, nhận được 6.",
  "instance": "/api/v1/predictions",
  "code": "invalid_frame_count",
  "errors": [ { "loc": ["query", "status"], "msg": "...", "type": "enum" } ]
}

errors chỉ có khi code = validation_error.

code HTTP Ý nghĩa
validation_error 422 Tham số / body sai kiểu, sai enum, thiếu trường
invalid_frame_count 422 Số ảnh ∉ [1, 5]
invalid_image 422 File không decode được thành ảnh
invalid_plate 422 Biển số review có ký tự ngoài A–Z, 0–9
invalid_zip · empty_zip · too_many_frames 422 Zip hỏng / không có ảnh LR / track > 5 ảnh
unsupported_media_type 415 Sai kiểu file
file_too_large · image_too_large · too_many_tracks 413 Vượt giới hạn
prediction_not_found · batch_not_found · not_found 404 Không có resource
batch_not_completed · batch_in_progress 409 Sai trạng thái batch
model_unavailable 503 Checkpoint chưa load được
database_unavailable · database_busy · database_timeout 503 DB mất kết nối / hết connection trong pool / query quá statement_timeout

Phân trang

Các endpoint trả về danh sách nhận page (bắt đầu từ 1) và page_size, rồi trả về:

{ "items": [ ... ], "total": 999, "page": 1, "page_size": 20 }

Trạng thái prediction (selective prediction)

status Điều kiện
accepted track_conf ≥ τ: tự động chấp nhận
needs_review track_conf < τ: đưa vào hàng chờ review
reviewed Đã có người sửa / xác nhận qua PUT /review

τ (PLATEREADER_CONFIDENCE_THRESHOLD) hiện là 0.90 (tạm). Giá trị chính thức sẽ chọn ở Tuần 5 sao cho precision ≥ 95% trên val. Với τ = 0.90, batch 999 track val có 887 track accepted và 112 track needs_review.

CORS, xác thực

  • CORS mặc định mở cho http://localhost:5173 (Vite). Đổi bằng PLATEREADER_CORS_ORIGINS.
  • Chưa có xác thực. API chỉ dùng cho mạng lab / demo. Nếu public qua Cloudflare Tunnel thì phải bật Cloudflare Access (Tuần 9).

License dữ liệu

API không lưu ảnh upload, chỉ lưu kết quả dạng text. Ảnh SR chỉ trả về một lần trong response, không ghi vào DB. Lý do: license ICPR26-LRLPR cấm phân phối lại ảnh dataset (xem tuan1_xac_nhan.md, câu 3).

Tài liệu kỹ thuật cho backend của prototype MF-SR-OCR, viết bám theo roadmap-3month-nhutminh.md (§1, §2, §4). Cập nhật: 22/10/2026 · Trạng thái: backend v1.0.0 chạy được trên Docker, frontend React sẽ làm sau (Tuần 8).

3. Luồng xử lý

3.1. Một track — POST /predictions (roadmap /predict)

Client ──multipart(1–5 ảnh)──► Router
  1. Validate: số frame 1–5, content-type JPG/PNG, ≤ 5 MB, decode được   ──lỗi──► 413/415/422 problem+json
  2. cv2 decode → RGB → Resize 32×128 → Normalize(0.5, 0.5); thiếu frame thì lặp frame cuối
  3. [threadpool] lock model → S1 forward (return_sr nếu include_sr) → log_probs [1, 16, 37]
  4. decode constrained | greedy → plate, track_conf
     + char_conf (Viterbi CTC alignment) + top-5 suggestions (constrained beam)
  5. status = accepted nếu track_conf ≥ τ, ngược lại needs_review
  6. [threadpool] INSERT predictions … RETURNING                     (connection lấy từ pool)
◄── 201 Created, Location: /api/v1/predictions/{id}, body JSON (+ sr_images base64 nếu yêu cầu)

3.2. Batch — POST /batches (roadmap /predict_batch)

Client ──zip──► Router: đọc ≤ 200 MB → parse zip trong RAM (không giải nén ra đĩa)
              → INSERT batches(status=queued) → submit job → 202 Accepted + Location
Worker (1 thread, các job xếp hàng tuần tự):
  status=running
  lặp mỗi 4 track:  lock model → forward → nhả lock
                    → 1 transaction INSERT 4 predictions
                    → UPDATE processed_tracks
  status=completed | failed(error)
Client poll GET /batches/{id} → GET /batches/{id}/predictions | /export (CSV)

3.3. Review — tab Review của React (Tuần 8)

GET /predictions?status=needs_review     → hàng chờ
GET /predictions/{id}/suggestions        → 5 nút chọn nhanh
PUT /predictions/{id}/review {plate}     → INSERT reviews + status=reviewed

5. Hiệu năng đo được (22/10/2026, MacBook Apple Silicon)

Phép đo Kết quả
1 track, chạy native (4 thread) ~270 ms
1 track, trong Docker Desktop 810–910 ms (3 lần đo)
Thành phần Forward model chiếm gần hết; decode + gợi ý + alignment ≈ 9 ms/track
Batch CPU: 32 track/lượt so với 1 track/lượt Không nhanh hơn (≈ 0.66 s/track cả hai), nên chọn lượt 4 track
Đọc DB trong lúc batch đang ghi p50 6–8 ms, p95 20–46 ms, 0 lỗi (xem §6)

Roadmap §4 đặt tiêu chí p95 ≤ 1 s cho 1 track trên CPU. Tiêu chí này sẽ đo chính thức ở Tuần 6/10 trên máy demo, không đo trên Docker Desktop của Mac.

6. Bài toán đọc / ghi liên tục

Phân tích đầy đủ, số đo và đề xuất mở rộng nằm trong report tuần 2 (tuan2_bao_cao.md, mục 5). Tóm tắt các biện pháp đã triển khai:

# Biện pháp Ở đâu
1 PostgreSQL thay SQLite: MVCC cho phép đọc không chặn ghi, ghi không chặn đọc docker-compose.yml, schema.sql
2 Connection pool 1–10, chờ tối đa 10 s rồi trả 503 database_busy kèm Retry-After db.py, errors.py
3 statement_timeout = 15 s cho mỗi connection, để query treo không giữ pool db.py
4 Không giữ connection DB trong lúc model chạy (inference xong mới mượn connection để ghi) routers/predictions.py, services/batches.py
5 Batch ghi theo lượt 4 track trong 1 transaction, cập nhật tiến độ sau mỗi lượt services/batches.py
6 Hàng đợi batch 1 worker, lượt nhỏ, nên request lẻ chen vào được sau tối đa 1 lượt services/batches.py, config.py
7 Review append-only (INSERT, không UPDATE đè), nên 2 người review cùng lúc không mất dữ liệu schema.sql (bảng reviews)
8 Thống kê batch tính bằng COUNT … FILTER lúc đọc, không có bộ đếm để tranh chấp db.py
9 Index cho 2 truy vấn nóng: hàng chờ review, kết quả theo batch schema.sql
10 Job đang chạy khi server restart được đánh failed, không bị treo running mãi main.py lifespan

7. Backup & khôi phục

Chính sách theo giai đoạn. Backup tự động chỉ cần khi DB chứa dữ liệu không tạo lại được.

Giai đoạn Dữ liệu trong DB Backup
Dev (Tuần 2–9) — hiện tại Prediction test: chạy lại model là có lại Tắt. Chụp tay khi cần: docker compose run --rm -e BACKUP_ONCE=1 backup
User test → demo (Tuần 10–12) Review do người thật nhập, kết quả SUS, thời gian review Bật: docker compose --profile backup up -d, 6 giờ / lần, giữ 7 ngày
Mốc bắt buộc chụp tay — Trước Tuần 6 (freeze), trước và sau Tuần 10 (user test), trước Tuần 12 (demo)
Mục Giá trị khi bật
Công cụ pg_dump -Fc -Z 6: backup logic, nén, chạy nóng (không dừng API)
Tần suất 6 giờ / lần (BACKUP_INTERVAL_HOURS), chụp 1 bản ngay khi service start
Lưu giữ 7 ngày (= 28 bản), tự xoá bản cũ (BACKUP_RETENTION_DAYS)
RPO (mất tối đa) ≤ 6 giờ dữ liệu
RTO (khôi phục) < 5 phút với backend/scripts/restore.sh <file> (đã chạy thử 22/10/2026)
Nơi lưu ./backups/ trên host, nằm ngoài volume DB. Trước demo copy thêm 1 bản sang ổ / cloud khác

Cron hay container? Mặc định dùng container backup chạy vòng lặp sleep, vì không phải cấu hình gì trên máy demo và lịch chạy đi kèm docker compose. Nếu deploy lên server cố định có cron thì thay bằng 1 dòng crontab gọi chế độ one-shot:

0 */6 * * *  cd /path/master’s_thesis_nhutminh && docker compose run --rm -e BACKUP_ONCE=1 backup

Lý do chọn 6 giờ và các phương án nâng cấp được trình bày trong report tuần 2 (tuan2_bao_cao.md, mục 6).

  • Postgres chỉ bind 127.0.0.1. Mật khẩu nằm trong .env (đã có trong .gitignore).
  • Container API chạy bằng user không phải root. Checkpoint mount read-only.
  • Zip đọc trong RAM, mỗi entry được giới hạn kích thước sau giải nén (chống zip-slip / zip bomb).
  • Chưa có xác thực. Trước khi public qua tunnel (Tuần 9) cần bật Cloudflare Access hoặc thêm API key.

9. Việc tiếp theo (theo roadmap)

Tuần Việc liên quan backend
3 Thêm CER/NED/Confidence-gap; dùng GET /predictions?batch_id= để lấy dữ liệu McNemar
5 Chốt τ (precision ≥ 95%) và cập nhật PLATEREADER_CONFIDENCE_THRESHOLD; track_conf đã có sẵn trong DB
6 Freeze: ghi model_version + SHA-256 từ GET /model vào freeze_manifest.json; đo latency p50/p95
7 parity_report.json từ backend/scripts/parity_check.py

Database schema — PostgreSQL 16

Nguồn: backend/app/schema.sql. API chạy file này mỗi lần khởi động; file idempotent (CREATE … IF NOT EXISTS). Roadmap §2 ban đầu ghi SQLite. Đã chuyển sang PostgreSQL vì cần đọc/ghi đồng thời (batch ghi liên tục trong lúc UI đọc và review ghi), backup nóng bằng pg_dump, và kiểu JSONB / UUID / TIMESTAMPTZ. Xem system-overview.md §6.

Bảng reviews

Lịch sử sửa tay. Chỉ thêm, không sửa / xoá (append-only).

Cột Kiểu Ràng buộc Mô tả
id BIGSERIAL PK Tăng dần, dùng để phân thứ tự khi 2 review cùng timestamp

Index idx_reviews_prediction (prediction_id, created_at DESC) dùng để lấy review mới nhất bằng LEFT JOIN LATERAL … LIMIT 1.

Tách review thành bảng riêng thay vì thêm cột vào predictions vì ba lý do:

  1. Giữ lịch sử, cần cho việc đo "thời gian review / số lần sửa" ở Tuần 10.
  2. Tránh ghi đè lẫn nhau khi 2 người cùng review 1 track: mỗi người INSERT một dòng riêng, không ai mất dữ liệu, kết quả có hiệu lực là dòng mới nhất.
  3. Cột plate của model không bao giờ bị sửa, nên vẫn tính lại được accuracy của model sau khi đã có review.

Truy vấn mẫu

-- Hàng chờ review, ký tự yếu nhất trước
SELECT id, track_id, plate, track_conf
FROM predictions
WHERE status = 'needs_review'
ORDER BY track_conf ASC
LIMIT 50;

-- Accuracy model vs accuracy sau review trên 1 batch có nhãn
SELECT
  AVG((p.plate = p.ground_truth)::int) * 100                         AS model_acc,
  AVG((COALESCE(r.plate, p.plate) = p.ground_truth)::int) * 100      AS after_review_acc
FROM predictions p
LEFT JOIN LATERAL (SELECT plate FROM reviews WHERE prediction_id = p.id
                   ORDER BY created_at DESC, id DESC LIMIT 1) r ON TRUE
WHERE p.batch_id = '3444f665-6ae0-4a31-8caf-c7a2526fd95b';

-- Precision của nhóm accepted theo τ (dữ liệu cho Tuần 5)
SELECT COUNT(*) FILTER (WHERE status = 'accepted')                                  AS n_accepted,
       AVG((plate = ground_truth)::int) FILTER (WHERE status = 'accepted') * 100    AS precision_accepted
FROM predictions WHERE ground_truth IS NOT NULL;

Xử lý (roadmap §2, flow bước 1–5)

  1. Validate: kiểu file, kích thước, số frame. Nếu ít hơn 5 frame thì lặp lại frame cuối cho đủ 5.
  2. Resize về 32×128, normalize (mean = std = 0.5), giống hệt pipeline val khi train.
  3. S1: STN → DCNv2 → FrameSR ×2 → ResBackbone (GN) → Attention Fusion → BiLSTM → CTC.
  4. Decode constrained hoặc greedy. Tính char_conf bằng CTC forced alignment, lấy top-5 gợi ý.
  5. So track_conf với τ để ra accepted hoặc needs_review, rồi ghi DB.

Gợi ý lấy từ cùng một lần constrained CTC prefix beam search dùng để decode (beam 16, mỗi vị trí ký tự bị khoá vào lớp chữ hoặc số theo layout LLLNLNN / LLLNNNN):

  • Hạng 1 luôn trùng với kết quả constrained_beam_decode trong src/utils/postprocess.py (có test kiểm chứng).
  • Các hạng sau là những chuỗi đầy đủ 7 ký tự còn lại trong beam, sắp xếp theo xác suất.
  • conf là trung bình hình học xác suất từng ký tự, cùng thang 0–1 với track_conf.
  • Gợi ý được tính lúc predict và lưu trong cột predictions.suggestions, nên endpoint này không chạy lại model.

Gợi ý luôn dựa trên constrained beam, kể cả khi prediction dùng decode=greedy.

POST /batches

Nhận dạng nhiều track từ 1 file zip. Đây là endpoint /predict_batch trong roadmap (Tuần 7). Batch 1.000 track trên CPU mất vài phút, nên request không chờ kết quả: server kiểm tra zip, đưa job vào hàng đợi rồi trả 202 Accepted ngay. Client theo dõi tiến độ bằng GET /batches/{id}, xong thì lấy kết quả qua /predictions hoặc /export.

Query

Tham số Kiểu Mặc định Mô tả

Cấu trúc zip

Giống thư mục dataset, nên có thể zip thẳng một thư mục val hoặc test:

tracks.zip
├── track_10007/
│   ├── lr-001.jpg … lr-005.jpg      ← 1–5 ảnh LR (.jpg/.jpeg/.png), sắp theo tên
│   ├── hr-001.jpg …                  ← bỏ qua
│   └── annotations.json              ← tuỳ chọn: {"plate_text": "AYG7579"} → tính accuracy
└── track_10011/ …
  • Thư mục cha gần nhất của ảnh được dùng làm track_id. Ảnh nằm ngay gốc zip được gộp thành 1 track, đặt tên theo tên file zip.
  • File hr-*, __MACOSX/ và file ẩn đều bị bỏ qua.
  • Zip được đọc thẳng trong bộ nhớ, không giải nén ra đĩa, nên không bị tấn công path traversal (zip-slip).

HTTP code Khi nào
